# Internationalisation

Serbian and English with next-intl, both locales statically prerendered. The rules that always apply are in `../CLAUDE.md`; this is the reasoning and the detail behind them.

## How the locale is read

`app/[locale]/layout.tsx` is the root layout (there is no `app/layout.tsx` above it), so `locale` is a root param. `packages/i18n/src/request.ts` reads it with `next/root-params` rather than `cookies()` or `headers()`: under `cacheComponents` either of those turns the subtree dynamic and nothing could be prerendered. `cacheComponents` switches root params on by itself, in Turbopack and webpack alike.

Limits of root params, both permanent or long-term:

- **Server Actions.** An action is not tied to a route. `sendB2bRequest` and `sendLocalizedContactEmail` take the locale as an argument and check it against the locale list before using it; the contact page binds it with `.bind(null, locale)` so the client form still calls a one-argument action.
- **Inside `"use cache"` on Next 16.1.** It throws there (support arrived in 16.3), and `locale()` has no generated type. Today the only `"use cache"` is `packages/shared/src/lib/api.ts`, which never touches next-intl.
- **Route Handlers.** `app/api/og` sits outside `[locale]` and reads query params, so it is unaffected.

## Routing

`localePrefix: "as-needed"` with a `pathnames` map in `i18n/routing.ts`. Each key is the internal route, the folder under `app/[locale]/`, and the value names only the locales that spell it differently, so a Serbian URL is its folder name and English is an alias (`/onama` and `/en/about`). `/sr/*` redirects to the bare path, so the two spellings never both rank. Legacy URLs from the live site are 308'd in `next.config.ts` (see `seo.md`); those redirects run before the proxy.

Locale detection and the locale cookie are both **off**. With detection on, `/` becomes a per-visitor redirect and stops being one cacheable document; with the cookie on, which URL a redirect lands on depends on hidden state (next-intl#1845). The prefix is the whole story.

`proxy.ts` (Next 16's name for `middleware.ts`) does the rewrite and runs on every matched request, including ones that end up serving a prerendered file. That is the price of keeping Serbian URLs unprefixed.

The language switch uses `getPathname` with a plain `next/link`, not next-intl's `Link` with a `locale` prop: that prop always emits a prefix, so switching back to Serbian would link to `/sr/...` and rely on a redirect. It sits in the navbar, which `@brand/shared` renders outside the page's `NextIntlClientProvider`, so it gets its own provider with an empty catalog (`messages={{}}`). Without it no English page prerenders.

## What is translated

Only copy written in this repo: `messages/{sr,en}.json`. Brand and catalog copy lives in PACMS and is not translated here, so a brand page's `<title>` on `/en` follows whatever the CMS holds. The B2B email body stays Serbian whichever language the form was filled in, because it goes to office@stridon.rs.

The legal pages are one HTML document per locale in the catalog, rendered through `Prose`, not dozens of ICU keys: statutory text has to stay diffable against what a lawyer approved. Only the two internal links are tokens (`__PRIVACY__`, `__CONTACT__`), filled in by `lib/legal.ts`.

`constants/*.ts` are module constants, evaluated at import with no locale in scope. They keep structure (route, icon, colour, photo, year) plus a message `key`, and the page pairs each key with its translation. Those keys are typed as unions of the catalog's keys, so a constant without copy fails `tsc`.

## Shared components and labels

`@brand/shared` has no i18n dependency. Every shared component keeps its Serbian as default labels and takes an optional `labels` object, plus an optional href where it links; passing nothing renders exactly what dck and sg-tools render. That is why `app/[locale]/layout.tsx` passes around twenty label props, and why shared `createRootMetadata` (Serbian, canonical `/`) is only used as a base that the layout overrides per locale.

Moving the translation into the shared package itself (shared components calling `useTranslations`, one shared catalog, every app on `[locale]`) was proposed on PR #14 and deferred by the repo owner. Keep it in mind when adding shared text.

## Client payload

`NextIntlClientProvider` receives an explicit `messages` of only the namespaces a client component reads (`Error`, `B2b`). Rendered from a Server Component without `messages`, it serialises the whole catalog into every page's flight payload, legal documents included; the explicit list took about 22 kB off every page.

## Metadata

Built by `lib/metadata.ts`, not the shared `createPageMetadata` directly, which takes one canonical and would make the English page point at the Serbian URL. Each page gets its own canonical plus `alternates.languages`, and `app/sitemap.ts` lists both locales with the same pairs. hreflang is `sr-Latn`, not `sr` or `sr-RS`: Serbian's default script is Cyrillic, and this site is Latin-only.

## Known: five failing prefetches per Serbian page

On a Serbian page the console shows a few 404s on `?_rsc=` requests. Nothing is broken: every link navigates and every page is prerendered. What fails is one of the two background requests Next fires to warm a link up.

For `/onama` the client router asks for the segment `/$d$locale/__PAGE__` while the tree has `/$d$locale/onama/__PAGE__`: it computes the key from the address bar, where the hidden `sr` prefix is missing, so it is one segment short. The English side is clean because `/en/about` carries its prefix; dck and sg-tools have no `[locale]` segment at all. It is the cost of `as-needed`; `always` would send every indexed Serbian URL through a redirect.

Measured on a full scroll of the Serbian homepage:

| | ok | failed | note |
|---|---|---|---|
| as shipped | 37 | 5 | the routes linked only from the navbar and footer |
| `prefetch={false}` on navbar + footer | 28 | 3 | worse: failures move to `/brendovi`, `/katalozi`, `/kontakt` |
| `prefetch={true}` on navbar + footer | 102-170 | 0 | clean, but roughly double the requests |

The owner chose to leave it. Why five routes fail rather than all of them was not established; Next's documented answer for links behind a proxy rewrite is passing `as` and `href` separately, which would change every link in `@brand/shared`.
